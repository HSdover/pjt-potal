# 작업 방향

작성일: 2026-05-19

## 현재 기준

초기 기준은 기능목록 엑셀을 화면 도메인/템플릿으로 분류하는 것이었지만, 현재 프로젝트에는 운영 기반과 개발 템플릿뿐 아니라 일부 실제 화면/API가 들어와 있다.

현재 구현된 실제 업무형 기능은 통합메타관리, 권한관리, 로컬/SAML 인증 골격, `/api/me`, 공통 예외/로깅, 외부 API 공통 클라이언트, 첨부/엑셀, Spring Batch 수동 실행 구조다. 파이프라인관리, AI데이터관리, 신청관리, DP뷰어, 공지사항 등은 아직 `MenuPlaceholderView.vue` 기반 placeholder다.

앞으로는 단순 설계 제안뿐 아니라 현재 소스 구조에 맞춰 프론트, 백엔드, DB, 권한, 운영 문서를 직접 구현/수정하는 작업을 수행한다. 단, 신규 외부 의존성 추가와 보안 파일 반입은 내부망/운영 제약을 고려해 별도 승인 항목으로 분리한다.

## 지금 할 일

1. 실제 구현과 문서가 어긋나면 `README.md`, 시스템 프롬프트, 운영/오프라인 문서를 같이 갱신한다.
2. placeholder 업무 화면을 실제 기능으로 전환할 때는 라우터, 권한, 프론트 API, 백엔드 Controller/Service/Repository, 로컬 H2 DDL/seed를 한 흐름으로 맞춘다.
3. 메뉴/권한 확장은 `설계/메뉴권한매핑설계.md` 기준으로 DB 메뉴관리와 기존 권한관리의 역할을 나눈다.
4. 운영 서버 투입 전에 env, Nginx, systemd, Redis, Oracle DB, SAML 또는 Knox 연동 값을 현장 정보로 치환한다.
5. 내부망 반입 전 `offline` 캐시, JDK, VS Code 확장, Git 서버 키트 같은 대용량 산출물과 Git 커밋 대상을 구분한다.

## 사용자 검토 체크리스트

| 확인 항목 | 판단 기준 |
|---|---|
| 도메인명 | 현업이 이해하는 메뉴 그룹명인가 |
| 화면명 | 기능목록 엑셀의 의도를 유지하는가 |
| 템플릿 유형 | 화면의 주 사용 방식과 맞는가 |
| 통합 가능성 | 비슷한 항목을 하나의 화면/탭으로 묶을 수 있는가 |
| 분리 필요성 | 같은 도메인 안에서도 사용 목적이 달라 별도 화면이 필요한가 |
| 보류 항목 | 엑셀만으로 판단하기 어려운 항목인가 |

## 다음 요청 순서

1. 기능목록 엑셀 기준 화면 도메인/템플릿 표를 보완한다.
2. 각 화면 후보를 독립 화면/탭/섹션 후보로 다시 나눈다.
3. 화면명과 메뉴명을 현업 용어 기준으로 다듬는다.
4. 프로젝트 투입 후 내부망 형상관리 전략을 상세화한다.
5. 프로젝트 투입 후 OCI Oracle Linux 운영 배포 전략을 상세화한다.
6. IAM/KNOX, DBA, OCI 담당자와 SAML/Oracle/Redis/외부 API 운영 값을 확정한다.

상세 화면 스펙 작성과 코드 구현은 현재 소스 기준으로 작은 단위로 진행하고, 운영/내부망 값은 담당자 확인 후 별도 반영한다.
